# 022 — i18n foundation (English + Brazilian Portuguese)

**Blocked by:** 003, 005 · **Blocks:** — (but see sequencing note)

## Goal

The app renders in **English** and **Brazilian Portuguese (`pt-BR`)**, with the language chosen per user and stored on their profile. This ticket lays the i18n *foundation* so that every screen built afterward (006–018) authors its copy through the message catalog from the start — never hardcoded, never retrofitted.

Reads the design from [ADR-0005](../../../docs/adr/0005-i18n-is-a-ui-layer-concern.md). Read it first; it settles what does and does not get translated, and why.

## Sequencing — do this before the screens

This ticket blocks nothing in the dependency graph, but **land it before ticket 006**. i18n is cheap when strings go in translated and ruinous as a retrofit. Once the foundation is here, tickets 006–018 pull every user-facing string from the catalog. The session player (011–014) especially: message catalogs are bundled into the JS at build time, so they are available offline for free — but only if the player reads from them rather than hardcoding.

## Scope

- **`next-intl`, "without i18n routing" mode.** No `[locale]` URL segment, no locale middleware rewrite. Provider wired at the root layout; locale resolved server-side from `profiles.locale`, falling back to a cookie + `Accept-Language` on the pre-auth sign-in screen (no profile exists yet there).
- **`profiles.locale` column** — a **one-line edit to ticket 003's `0001_init.sql`**, not a new migration (003 isn't built yet):
  ```
  locale text NOT NULL DEFAULT 'en'   -- 'en' | 'pt-BR'
  CHECK (locale IN ('en','pt-BR'))
  ```
  RLS is already covered by the `profiles` policy (`id = auth.uid()`) — add no new policy. Regenerate types after.
- **Seed locale at profile creation** — in ticket 005's `handle_new_user` path, set `locale` from the request's `Accept-Language` (map any `pt*` → `'pt-BR'`, else `'en'`) so the stored value is honest from the first render.
- **Message catalogs** — `messages/en.json` and `messages/pt-BR.json`, containing:
  - UI chrome (buttons, labels, `"Last time:"`, errors, empty states) — seed what the scaffold and shell already show.
  - **Enum display labels**, keyed by DB value: `muscle_group.{chest,back,shoulders,quads,hamstrings,glutes,biceps,triceps,core,calves,other}` and `equipment.{barbell,dumbbell,machine,cable,bodyweight,kettlebell,other}`. These are the *only* DB-originated strings that get translated.
- **Locale switcher** — a control (in settings / profile) that writes `profiles.locale` via a Zod-validated Server Action and re-renders. Mirror how `weight_unit` is changed.
- **Locale-aware formatting** — route number/date formatting through `next-intl`'s `Intl` wrapper so `pt-BR` gets `1.234,5` and its date order. Note: **weights are still stored in kg and converted at the edge per `weight_unit`** — locale governs *formatting*, `weight_unit` governs *unit*. Two independent axes; don't conflate them.

## The traps

1. **Do not translate the 60 seeded exercise names, and do not add a translations table.** ADR-0005 chose Option B deliberately. The catalog names read identically in both locales; the name is the identity key. Custom exercises stay in the user's own words. If you find yourself writing `exercise_translations`, stop — that's a deferred future ticket, not this one.

2. **Enums are keys in the DB, labels in the catalog.** `muscle_group` stays `'chest'` in Postgres. Never store `'peito'`. Translate only on render.

3. **No `[locale]` segment.** If you reach for `app/[locale]/` or next-intl's routing middleware, you've contradicted decision 1 of ADR-0005 and restructured the scaffold for nothing.

4. **The pre-auth surface has no profile.** The sign-in screen must resolve locale from cookie + `Accept-Language`, not from `profiles.locale` (which doesn't exist yet for a logged-out visitor).

## Acceptance

- A user can switch language between English and `pt-BR`; the choice persists to `profiles.locale` and survives reload.
- A new `pt-BR`-browser user lands on a Portuguese app on first sign-in (locale seeded from `Accept-Language`).
- The exercise picker shows **translated enum labels** (muscle group / equipment) around **untranslated** catalog exercise names — as designed.
- Numbers and dates render in the `pt-BR` format when that locale is active; weights still honor `weight_unit` independently.
- `supabase db reset` applies the `locale` column cleanly (folded into `0001_init.sql`); `npm run test:rls` still passes unchanged.
- No `[locale]` route segment exists anywhere.
